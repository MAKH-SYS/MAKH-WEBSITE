Attacking a kernel from ring 3 with an oracle

MakhOS engineering · UFUZZ (release 1.4) · drawn from the public design docs

KFUZZ fuzzes the kernel from the inside. UFUZZ attacks it the way a hostile program really would — from ring 3, through the syscall interface — and it is built around one uncomfortable question: a fuzzer is only as good as its oracle, so how do you know the oracle is right? An oracle that shares the generator's mistakes is blind exactly where it matters most.

UFUZZ's answer is that every verdict can be checked. Instead of the usual "did it crash?", every generated syscall carries the result the ABI contract requires — not a vague expectation, but -EBADF, slot 3, O_RDWR. Any errno the kernel returns must be one the inventory documents. And every replay pass must leave the file-descriptor table exactly as the worker found it.

Typed programs over a contract

The campaign starts from an ABI inventory of 80 syscalls — 48 implemented, 25 partial, 7 stub — with every pointer's direction and size, every resource's lifecycle, and every documented errno written down. From that, a dependency-aware generator emits typed programs as an intermediate representation: a program that opens a file and then reads it knows the read depends on the open's returned fd. Each call in the IR is paired with its expected result, and a Python structural validator checks every generated program before it ever runs.

The programs then run in an isolated ring-3 worker under a watchdog, with net-zero page and heap accounting and a baseline-relative fd model. A worker that crashes does not stop the campaign; the supervisor turns a VM timeout into a KERNEL_HANG record and reboots to continue.

The oracle that is itself checked

Here is the part that makes UFUZZ unusual. A second, independent model re-derives every expectation from the same ABI inventory and the kernel's own headers — separately from the generator. The two must agree on all 4099 generated programs. If they ever disagree, either the kernel is wrong or one of the two models is, and both cases are worth knowing. Mutation tests deliberately break each side to prove the agreement genuinely depends on both — an oracle that can't be made to disagree isn't checking anything.

This discipline caught its own mistakes, too. In three campaigns, 22 of the 26 programs the mutated arms flagged turned out to be errors in the independent deriver itself (an fd bind takes whatever the call returns) — now fixed and pinned by tests. The oracle improving the oracle is the point.

From disagreement to a one-line reproduction

When the kernel and the expectation disagree, the event becomes an artifact: classified, deduplicated by signature, stamped with the build it came from, and carrying a command that replays it in a fresh boot. Then it is shrunk. A delta-debugging (ddmin) minimizer removes calls as long as the finding keeps the same signature at a declared threshold, so the reproduction collapses to its essence. Three planted kernel bugs minimized from 24–26 calls down to 2, 1 and 7 calls respectively.

# replay one program deterministically, in a fresh boot
make test-suite SUITE=ufuzzreplay REPLAY=5:3:23758

# triage a campaign log into deduplicated, replayable artifacts
python3 tools/ufuzz_triage.py build/suite.log --check

The first natural finding: UF-F001

A fuzzer earns its keep when it finds a bug nobody planted. UF-F001 was found by the structure-aware mutation engine in three independent campaigns: a zero-length read or write returned 0 without validating the file descriptor. So write(-1, buf, 0) returned 0, where both the ABI contract and Linux say it must return -EBADF. No data or privilege impact — but a real contract violation. The fix makes a zero-length call report exactly the fd error a one-byte call would, and the committed reproducer is now a permanent regression test (ufuzz.uf_f001_zero_length_validates_fd): four programs failed before the fix, all pass after.

Measured, not assumed

It would be easy to claim coverage-guided mutation beats random generation and move on. UFUZZ instead measured it, under a rule fixed before the campaigns ran — and reported the honest result: no measurable difference on this particular surface. The 1.4 release is tagged with two conditions openly left open (user-space coverage domains and a single-CPU race mode), because nothing is claimed that wasn't shown. Race testing is explicitly deferred to the multiprocessing line, where it can be measured on more than one CPU rather than simulated on one.

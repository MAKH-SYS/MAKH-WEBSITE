How a kernel fuzzes itself without triple-faulting

MakhOS engineering · KFUZZ (Phase 15) · drawn from the public design docs

A fuzzer feeds a program random input and watches for crashes. Doing that to a kernel usually means an external harness — syzkaller-style — driving it from user space through syscalls. MakhOS does something less common: it fuzzes its kernel from the inside, in ring 0. A sandboxed kernel thread generates random inputs and calls the kernel's own functions directly — the heap allocator, the physical page allocator, memmove, the pthreads API, the shell parser and the network receive path — at full speed, with no privilege boundary in the way.

The obvious problem: a bad input in ring 0 normally kills the machine. A stray write faults, the fault handler faults, and the CPU triple-faults into a reset. The whole trick of KFUZZ is to make those faults survivable and reproducible — every crash is caught, tagged with the exact seed that produced it, and the campaign keeps going.

The ring-0 sandbox

The core is a setjmp/longjmp pair written in assembly (kernel/kfuzz/jmp.asm), because the freestanding kernel has no libc to borrow one from. One iteration looks like this:

int jumped = kfuzz_setjmp(sb.jb);   // save callee-saved regs, rsp, return addr
if (jumped) {
    // arrived here via a fault -> longjmp; sb.fault_* describe it
    if (sb.cleanup) sb.cleanup();   // drop any lock the target held
    log("CRASH seed=... vector=... replay: fuzz replay ...");
    return CRASH;
}
sb.active = 1;
target->fn(&rng, iters);            // may fault anywhere, arbitrarily deep
sb.active = 0;

The second half of the magic is in the interrupt descriptor table. When a CPU exception (vectors 0–31) fires while the sandbox is active, the handler in kernel/arch/idt.c hands control to the sandbox instead of panicking:

if (vector < 32 && kfuzz_in_sandbox())
    kfuzz_report_fault(regs);       // records vector/rip/cr2, then longjmp

kfuzz_report_fault() records the fault and longjmps back to the harness. One subtlety that would otherwise bite: the fault was taken through an interrupt gate, which clears the interrupt flag, so kfuzz_longjmp ends with an explicit sti — otherwise the harness would resume with interrupts off and the next timer tick would never arrive.

Locks across a fault are the one place the abstraction leaks. A target that holds a real mutex — only netrx, which takes net_lock around net_input — registers a cleanup callback. On recovery the harness calls it to release the lock, or the next iteration would deadlock. Everything else is guarded only by IRQ-off critical sections, which the sti already restores.

This is validated, not asserted on faith. A dedicated test, kfuzz.sandbox_recovers_from_page_fault, runs a target that deliberately writes to an unmapped canonical address, then checks that the #PF was caught and that the kernel is fully functional afterwards — it allocates, walks the heap, and runs a clean campaign.

Coverage feedback, cheaply

A blind fuzzer wastes almost all its time re-exploring the same paths. KFUZZ is coverage-guided: the subject files — kheap.c, pmm.c, string.c, shell.c and the whole net/ stack — are compiled with -fsanitize-coverage=trace-pc, so GCC emits a call at every basic block:

void __sanitizer_cov_trace_pc(void) {
    if (!cov_enabled) return;
    uint64_t pc  = (uint64_t)__builtin_return_address(0);
    uint32_t idx = (uint32_t)((pc * GOLDEN) >> 48) & (COV_BITS - 1);
    cov_map[idx >> 6] |= 1ull << (idx & 63);     // set a bit; idempotent
}

Setting a bit is idempotent, so no lock is needed — a rare lost update under preemption only under-counts, it never corrupts. The harness itself is deliberately not instrumented, so the map measures the code under test rather than the fuzzer. A seed that raises the edge count is kept in a small corpus (up to 64 entries); each iteration either mutates a corpus seed or draws a fresh one, so inputs that reach new code are favoured. That is coverage-guided fuzzing in miniature.

One seed, exactly reproducible

Reproducibility is what turns a crash into a bug report. Every iteration is driven entirely by one 64-bit seed through an xorshift64* generator — three shifts and a multiply — so a finding replays bit-for-bit:

MakhOS> fuzz replay 0x609a5f1aa29f9058 netrx
replay seed=0x609a5f1aa29f9058 target=netrx -> clean

The crash log prints that exact command for you. No saved input file, no flaky "it happened once" — just the seed.

Oracles: catching corruption that never faults

Not every bug is a fault. A double-free or a buffer overrun can leave the machine running but the kernel's invariants quietly broken. So after every target run, three oracles must hold or the seed is reported as an ORACLE FAIL:

  • kheap_check() — every heap block's magic, size, alignment and footer, the free list, and the heap_used accounting are all consistent.
  • kheap_get_bad_frees() — unchanged, so no double or wild free slipped through.
  • proc_tree_check() — the process tree's parent/child links are intact.

These are the same oracles that were built during an earlier bug hunt in the networking stack, now doing permanent duty. And because a target can hang rather than crash, a high-priority watchdog thread reads a heartbeat the campaign bumps each iteration; if it stops advancing for more than four seconds, the watchdog panics with the culprit seed. That is not hypothetical — it fired the first time the shell target was allowed to run ping to an unreachable host, which blocks for seconds on ARP timeouts. A real "this input takes too long" finding.

What it proves

Across the test and stress runs, the heap, pmm, string, pthread, shell and netrx targets run clean over hundreds of thousands of iterations — strong evidence that those subsystems handle random and malformed input without faulting, leaking, or breaking their invariants. The sandbox recovery itself is proven by the page-fault injection test. The self-fuzzer is now permanent infrastructure: every make test runs it, and make stress runs the whole thing 20+ times in parallel. A new subsystem gets fuzzed for free by adding a target and, if it has integrity invariants, wiring them into oracles_ok().

Giving the fuzzer its own CPU: the MakhOS fuzz cell

MakhOS engineering · MakhOS 2.0 (SMP) · commercial edition

MakhOS 1.x ran on a single CPU. MakhOS 2.0 is symmetric multiprocessing — it boots every core the firmware reports and runs one scheduler across all of them, with real lock discipline underneath. That is table stakes. The interesting part is what the extra cores made possible: a way to run the kernel's own fuzzer on a CPU of its own, and to contain what it finds — a fault, a broken invariant, or a hang — on that one core, while the rest of the machine keeps working.

We call it a fuzz cell. This post is about why it is hard and how it is built.

The starting point: a kernel that fuzzes itself

MakhOS already fuzzes its kernel from the inside. KFUZZ runs a sandboxed kernel thread that calls the kernel's own functions — the heap, the page allocator, the filesystem, the network path — with random input, catches the faults that result with an assembly setjmp/longjmp sandbox, and turns each one into a reproducible finding tagged with its seed. On one CPU, that campaign shares time with everything else.

The question 2.0 asks: what if fuzzing had its own core? Then it could run flat-out without stealing time from real work — and, more importantly, a crash or a hang inside it could be kept off every other core. That is only worth doing if the containment is real. It took the whole SMP stack to get there.

The foundation

Before a cell can be carved off, the kernel has to be genuinely multi-core and genuinely safe about it. MakhOS 2.0 adds, brick by brick, each with a test written to fail first:

  • A fair ticket spinlock with lock levels and a lockdep-lite checker that refuses an out-of-order or re-entrant acquire — plus an audit that tags every mutable global with why it is safe.
  • APIC-era interrupts: ACPI (MADT) discovery, the Local and I/O APICs, and a per-CPU timer.
  • AP boot: a 16→32→64-bit trampoline and INIT-SIPI-SIPI to bring every application processor online, each with its own GDT/TSS/IST/GS.
  • Cross-CPU IPIs and a TLB shootdown that keeps every core's view of the page tables coherent.
  • One SMP scheduler: a single run queue, a barrier-correct wake-up handshake (validated against a Dekker litmus test), CPU affinity, and per-thread FPU and segment state so a thread survives migration.
  • A deterministic concurrency simulator that runs the real lock and scheduler code, byte-identical, under a seeded and replayable scheduler, with a KCSAN-lite race detector on top.

Carving off a cell

With that in place, a cell is one CPU taken out of the scheduler. The first kind is a silent cell: its timer tick is masked, it refuses IPIs, and it runs an isolation workload with a deferred, epoch-gated TLB flush — a low-noise core, the OS equivalent of isolcpus/nohz_full.

The fuzz cell is the second kind, and it is different in one crucial way: it still runs the shared kernel. Its targets take the kernel's real locks, allocate from its real heap, and keep the tick and the IPIs. What it isolates is not memory — it is control: where a fault lands, who gets reported, who is stuck.

A fault, caught on the cell's CPU

The sandbox that catches a CPU fault had to become per-thread. On one CPU, "a target is running" is a single flag. With several cores, a fault on CPU A while CPU B is fuzzing must not be mistaken for B's — or the fault handler would longjmp onto the wrong stack. So the sandbox now belongs to the exact thread running the target; a vector-0–31 fault is the fuzzer's only if it is taken by that thread, on that core. Everything else stays fatal, as it should.

Each caught fault is counted per CPU and sent to the root as a finding — kind, vector, seed, CPU — over a lock-free channel. In the registered evaluation, the deliberate-fault target run 1000 times in the cell, at 2, 4 and 8 CPUs, lands 1000 faults on the cell's core and zero on any root core, every time, and the campaign runs to its end. A canary confirms the converse: a fault raised on a root thread while the cell's sandbox is active is not swallowed by that sandbox — 20 times out of 20.

The hard part: containing a hang

A fault is a clean event — the CPU traps, you catch it. A hang is not. A target stuck in an infinite loop, or deadlocked on a lock, never traps; it just stops making progress. Before 2.0, KFUZZ handled that with a watchdog that panics — it brought the whole machine down. For a fuzz cell, that is exactly the wrong answer.

So the fuzz cell's watchdog runs on a root CPU — because the cell's own core may be the one that is wedged. When a target sits in the sandbox past the budget without the campaign advancing, the watchdog does three things instead of panicking: it reports the hang on the findings channel with its seed; it names, loudly, the locks the cell's CPU is holding; and it quarantines the cell — the stuck core is not handed back, and no lock is released by force. The machine stays alive.

The test that proves it was, as always, written to fail first. A new test target that spins forever is run in a fuzz cell:

// before 2.0's containment:
*** KERNEL PANIC *** KFUZZ watchdog: target 'spin' hung on seed 0x7a4d...

// after:
[KFUZZ] HANG target=spin seed=0x7a4d... cpu=1 held=[]   (reported)
[CELL]  fuzz cell on CPU 1 quarantined: target hung; CPU not returned

The first line is the old behaviour, reproduced on purpose by forcing the pre-2.0 path: the machine dies. The second is 2.0: the hang is a finding, the core is quarantined, and the test returns — which is the whole point.

Honest about the limits

A fuzz cell contains control, not memory. It runs the shared kernel, so a target that corrupts the shared heap corrupts the root's heap too, and a hang that holds a global lock will make the root paths that need that lock wait — the hang report says exactly which lock. Forcibly unwinding a stuck target's locks, and restoring kernel state after a corrupting run with snapshots, are deliberately out of scope for this version. These are written down in the design log, not papered over.

That discipline is the point as much as the feature is. Every brick ships with a test that failed first, a positive and a negative canary for each oracle, and numbers that are measured, not judged: the full suite passes at 1, 2, 4 and 8 CPUs; fault containment and hang containment are evaluated against criteria registered before the work; the fuzz cell's throughput is reported as a figure (about 17% under the same campaign on a root core — the cost of the channel, the watchdog, and the isolation), not a verdict.

Every finding replays deterministically from its seed on a root CPU, and the whole fuzz cell is driven from the shell — fuzzcell start, fuzzcell poll, fuzzcell stop — so a campaign can be launched and its findings read from an ordinary user program, not just from inside the kernel.

Where it goes

The fuzz cell is the first thing built on the cell abstraction, and the cell abstraction is built to take a type: a silent cell, a fuzz cell — and, later, an application cell that gives a latency-sensitive workload a core with no scheduler jitter, or a hypervisor that runs a guest under second-level paging and snapshots it for fuzzing. Same mechanism, different payload.

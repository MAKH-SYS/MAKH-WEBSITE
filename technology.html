How MakhOS works

🔬 KFUZZ ring-0 self-fuzzer · since Phase 15

A bad input in ring 0 normally kills the machine. KFUZZ makes it a finding: a coverage-guided fuzzer that runs inside the kernel, calls the kernel's own functions directly, survives the CPU faults it provokes, and prints the exact seed to reproduce each one.

The ring-0 sandbox

  • setjmp / longjmp in assembly (kernel/kfuzz/jmp.asm) — the freestanding kernel has no libc. A fault inside a target unwinds back to the harness instead of halting the machine.
  • Fault interception — when a CPU exception fires while the sandbox is active, arch/idt.c calls kfuzz_report_fault() (recording vector, RIP, CR2) and longjmps back, ending with sti so interrupts are live again.
  • Locks across a fault — a target holding a real mutex (only netrx, which takes net_lock) registers a cleanup callback so the next iteration can't deadlock.
  • Proven, not assumed — a test deliberately writes to an unmapped address and asserts the #PF is caught and the kernel is fully functional afterwards.

Coverage, oracles & reproducibility

  • Coverage-guided — subject files are built with -fsanitize-coverage=trace-pc; GCC emits a hook at every basic block, and seeds that reach new edges are kept and mutated. The harness itself is not instrumented.
  • Three invariant oracles run after every iteration: the heap walker (kheap_check), the bad-free counter, and the process-tree check — catching silent corruption that never faults.
  • Deterministic replay — every iteration is driven by one 64-bit seed, so fuzz replay <seed> <target> reproduces any finding exactly.
  • Watchdog — a high-priority thread panics with the culprit seed if a target stops advancing for more than 4 seconds.

🔍 UFUZZ ring-3 syscall fuzzer · since 1.4

KFUZZ fuzzes the kernel from the inside; UFUZZ attacks it the way a hostile program does — through the syscall interface, from ring 3. It knows the result each call must return, and is built so that every verdict can itself be checked.

An oracle that is itself checked

  • Every call carries its required result — not "didn't crash", but -EBADF, slot 3, O_RDWR. Any returned errno must be one the inventory documents.
  • A second, independent model re-derives every expectation from the ABI inventory and the kernel headers; the two must agree on all 4099 generated programs, and mutation tests prove the agreement depends on both sides.
  • Net-zero accounting — isolated ring-3 workers under a watchdog, with page/heap net-zero checks and an fd baseline that every replay must restore.

Triage → replay → minimize

  • Every event becomes an artifact — classified, deduplicated by signature, carrying the build it came from and a command that replays it in a fresh boot.
  • Findings shrink to their essence — ddmin minimization, accepted only on the same signature: three planted bugs reduced from 24–26 calls to 2, 1 and 7.
  • Measured, not assumed — coverage-guided mutation vs random generation was compared under a rule fixed in advance; the honest verdict (no measurable difference on this surface) is reported as measured.
The first natural finding

UF-F001 — found by the mutation engine in three independent campaigns, not planted: a zero-length read/write returned 0 without validating the fd (write(-1, buf, 0) == 0, where the contract and Linux say -EBADF). Fixed, with the reproducer committed as a permanent regression test.

🧱 Architecture x86-64 · GRUB / Multiboot2

MakhOS boots with GRUB (Multiboot2), brings up the x86-64 platform, and layers a real userland on top: paging with copy-on-write, a preemptive scheduler, POSIX threads, a VFS with ext2, and ring-3 processes that run unmodified musl and busybox binaries.

Boot & platform

GRUB / Multiboot2 brings the kernel up; it draws to a framebuffer graphics console and programs the GDT, IDT, PIC, PIT and TSS. A higher-half kernel maps itself to the top of the address space.

Memory

A bitmap physical allocator and a paging VMM with per-process address spaces, copy-on-write fork, and NX / W^X. The kernel heap carries a full integrity walker and stack canaries checked on every context switch.

Scheduling

Priority run queues with quantum-based preemption at the IRQ tail, sleep and wait queues with timeouts, an idle reaper for detached threads, and clean POSIX threads (mutexes, condvars, semaphores, TLS).

🌐 Networking PCI + e1000 · RFC 793 TCP

A real network stack from the PCI bus up to a POSIX socket API: an Intel e1000 NIC driven over DMA, ARP / IPv4 / ICMP / UDP, and a full RFC 793 TCP state machine — one lock, one worker thread, trivially free of lock-order bugs.

The hardware & the model

  • PCI + e1000 — configuration mechanism #1, a full bus scan, BAR decoding and bus mastering; 32-descriptor RX/TX rings, IRQ-driven receive, MAC read from the EEPROM.
  • One lock, one worker — every piece of protocol state lives under net_lock. IRQ handlers only sem_post; netd does all parsing in thread context.
  • Full TCP — all RFC 793 states, 16 KB send/receive rings, flow control with zero-window probing, RTO 300 ms → 3 s, fast retransmit on 3 duplicate ACKs, and a short TIME_WAIT.

🧩 Self-hosting tcc + GNU make on MAKH

MakhOS runs a real C compiler and build system on itself. It rebuilds a program it ships — from its own shipped source — and the rebuilt binary behaves identically. It also runs unmodified busybox and musl static-PIE binaries as ordinary ring-3 processes.

A toolchain on the OS

  • tcc runs as a ring-3 program, doing codegen → object → link internally, so MAKH never needs an external as or ld.
  • GNU make drives tcc across a multi-file project via fork/exec/wait.
  • One source of truth — the thing MAKH rebuilds is literally its own shipped user/musl/hello.c, copied into the initrd; there is no second copy to drift.
  • That the rebuilt binary exits 42 proves tcc's codegen, musl's crt, MAKH's arch_prctl TLS, the heap syscalls and the stdio path are all correct together.

Real, unmodified binaries

  • musl + busybox static-PIE executables run as ordinary ring-3 processes — a static-PIE ELF loader with full auxv and the per-process FS base for TLS.
  • Full process primitives: fork (copy-on-write), execve, wait4, pipes, job control and signals.
  • A higher-half kernel freed 0x400000 for standard non-PIE binaries, which is what makes tcc's own output loadable.
  • Persistent storage via a polled virtio-blk disk and a read/write ext2 filesystem, up to multi-block-group and triple-indirect files.

🖥️ The shell framebuffer console · ring-3 /bin/sh

MakhOS boots to a fennec splash with a spinning loader, then hands off to an interactive ring-3 /bin/sh on a framebuffer graphics console — a raw-mode line editor with command history, pipelines, job control and about 25 commands.

  • Framebuffer console — GRUB gives a 1024×768×32 linear framebuffer; MAKH renders antialiased 8×16 glyphs over a warm 16-colour palette, with a VGA-text fallback and an unchanged serial mirror.
  • Raw-mode line editor — the shell flips the terminal to raw mode via termios / TCGETS / TCSETS, owns the line, and echoes it itself.
  • Command history — a ring of the last 32 entries; Up/Down walk it, with navigation keys delivered as ANSI escapes.
  • Editing shortcuts — Left/Right, Ctrl+A/E (line start/end), Ctrl+U/K (kill), Backspace/Delete.
  • Pipes & job control — a | b pipelines, each command its own process group, Ctrl+C / Ctrl+Z hitting the job and not the shell.
  • UX — a prompt that shows the cwd, TAB completion for commands and paths, redirection (> >> <) and heredocs, and a cyan block cursor.
